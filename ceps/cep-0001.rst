## Abstract

This proposal specifies the lexical grammar, 21 orthogonal atomic operations,
predefined permission macros, compile-time semantic validation rules, and runtime
evaluation pipeline of **CACL (CFMS Access Control Language)**.

CACL is a declarative access control domain-specific language (DSL) tailored for
hierarchical directory trees and immutable versioned document models, with a default
file extension of `.cacl`. Backed by structured relational data as its Single Source
of Truth (SSOT), CACL compiles deterministically via an LALR(1) parser into bitmasks
and Boolean condition trees, and supports lossless decompilation back into canonical
DSL text.

---

## Motivation

In the Confidential File Management System (CFMS), conventional flat Role-Based
Access Control (RBAC) or monolithic Access Control Lists (ACLs) cannot simultaneously
satisfy four core engineering and security requirements:

1. **Controlled inheritance truncation and expressive condition matching**: Business
directory administrators need explicit `inherit off` boundaries to isolate
subdirectory permissions, while combining static principal grants with dynamic
Boolean predicates under unambiguous deny-overrides semantics.
2. **Semantic coupling of directories and documents**: When directory listing and
document reading share a single permission flag, tree inheritance cannot express
common collaboration patterns such as a "blind dropbox" (allowing users to list a
directory or submit files while denying read access to existing documents).
3. **Historical data leakage in an immutable revision model**: Every write to a CFMS
document produces a new immutable revision. Without separating access to the
current revision from access to historical revision bodies, sensitive information
redacted in a newer version could still leak via older snapshots.
4. **Clear boundaries with soft deletion and global query filters**: CFMS uses global
query filters to completely exclude soft-deleted objects from standard business
views. The permission model must align strictly with this mechanism to avoid
defining redundant permissions that are unreachable through standard endpoints.

---

## Rationale

* **Unified DACL Model with Deny-Overrides and Inheritance Truncation**: All rules
reside in an inheritable, truncatable Discretionary Access Control List (DACL)
composed of peer-level `allow` and `deny` rules governed by `READ_DACL` and
`WRITE_DACL`. Evaluating effective rules with strict deny-overrides, default-deny
fallback, and explicit `inherit on | off` boundaries keeps resolution deterministic
while letting subdirectories establish isolated permission trees.
* **Orthogonal Atomic Operations and Compile-Time Macro Expansion**: All atomic
operations are mutually orthogonal and map directly to fixed-offset bitmasks,
eliminating logical conflicts between "implied containment" and set subtraction.
Permission macros (Presets) are expanded into deterministic bitmasks at compile
time, preventing future macro updates from silently escalating privileges on
existing directories.
* **Explicit Inheritance Scope**: Declaring propagation targets explicitly via
`on self | dirs | docs | all` prevents unintended spillover of directory-level
grants onto child documents.
* **Transient Comments vs. Persistent Remarks**: Line comments beginning with `#` are
intended solely for temporary human reading during editing and are discarded at
compile time. Audit explanations that must persist alongside policies are expressed
as first-class `remark "..."` clauses, preserving semantic purity across
compile/decompile round-trips.

## Specification

### 1. Terminology and Conventions

* **Language Identifier**: `CACL` (CFMS Access Control Language), using the `.cacl` file extension and UTF-8 encoding.
* **Object Types**: Namespace nodes are classified into **Directories** and **Documents**. A document maintains a system-managed sequence of immutable **Revisions**, exactly one of which is designated as the active (`current`) revision.
* **Object States**: Objects exist in either the **Normal** state or the **Soft-Deleted** state. Objects in the soft-deleted state are completely hidden from standard endpoints by global query filters and are visible only through dedicated trash management endpoints.

---

### 2. Predefined Atomic Operations (21 Operations)

Every atomic operation is assigned a permanent, immutable bit offset (`0` through `20`, with higher bits reserved for future expansion), enabling compact storage as unsigned integer bitmasks and fast bitwise evaluation.

#### 2.1 Directory-Specific Operations

| Bit Offset | Mask (Hex) | Operation | Applicable State | Semantics & Constraints |
| --- | --- | --- | --- | --- |
| `0` | `0x000001` | `TRAVERSE` | Normal | Traverse through a directory to access descendant paths; does not grant directory listing rights. |
| `1` | `0x000002` | `LIST_DIRECTORY` | Normal | List basic entry metadata (ID, name, type) of non-deleted direct children in the directory. |
| `2` | `0x000004` | `CREATE_DOCUMENT` | Normal | Create a new document in the directory; also required on the destination parent directory when reparenting a document into it. |
| `3` | `0x000008` | `CREATE_DIRECTORY` | Normal | Create a new subdirectory in the directory; also required on the destination parent directory when reparenting a directory into it. |

#### 2.2 Document and Immutable Revision Operations

| Bit Offset | Mask (Hex) | Operation | Applicable State | Semantics & Constraints |
| --- | --- | --- | --- | --- |
| `4` | `0x000010` | `READ_CONTENT` | Normal | Read the body content of the document's active (`current`) revision only. |
| `5` | `0x000020` | `WRITE_CONTENT` | Normal | Write document content; the system automatically creates a new immutable revision and advances `current` to it. |
| `6` | `0x000040` | `LIST_REVISIONS` | Normal | List a document's historical revision inventory and basic revision metadata, excluding historical body content. |
| `7` | `0x000080` | `READ_REVISION` | Normal | Read the body content of non-current historical revisions of a document. |
| `8` | `0x000100` | `SET_CURRENT_REVISION` | Normal | Point the `current` pointer to a specified historical revision without mutating any historical snapshot. |
| `9` | `0x000200` | `DELETE_REVISION` | Normal | Permanently destroy a specified historical revision (high-risk, irreversible). **Business invariant**: Deleting the `current` revision or the sole remaining revision of a document is strictly prohibited. |

#### 2.3 Common Namespace and Metadata Operations (Directories & Documents)

| Bit Offset | Mask (Hex) | Operation | Applicable State | Semantics & Constraints |
| --- | --- | --- | --- | --- |
| `10` | `0x000400` | `READ_METADATA` | Normal | Read extended metadata of an object (custom tags, classification attributes, extension fields, etc.). |
| `11` | `0x000800` | `WRITE_METADATA` | Normal | Update extended metadata of an object. |
| `12` | `0x001000` | `RENAME` | Normal | Rename an object within the same parent directory (e.g., `aaa/bbb → aaa/ddd`). |
| `13` | `0x002000` | `REPARENT` | Normal | Change an object's parent directory (e.g., `aaa/bbb → ccc/bbb`). Must pass destination parent directory creation checks (`CREATE_DOCUMENT` or `CREATE_DIRECTORY`). |

#### 2.4 Lifecycle and Trash Operations

| Bit Offset | Mask (Hex) | Operation | Target Object | Applicable State | Semantics & Constraints |
| --- | --- | --- | --- | --- | --- |
| `14` | `0x004000` | `DELETE` | Directory / Document | Normal | Mark an object as soft-deleted. |
| `15` | `0x008000` | `DIRECTORY_DELETE_CHILD` | Directory | Normal | Bypass per-item DACL `DELETE` checks on descendants when soft-deleting a directory. |
| `16` | `0x010000` | `LIST_DELETED` | Directory | Normal / Soft-Deleted | List soft-deleted child entries under a directory (restricted to dedicated trash endpoints; returns basic display fields with the listing). |
| `17` | `0x020000` | `RESTORE` | Directory / Document | Soft-Deleted | Clear the soft-deleted state. For directories, requires the target parent directory to be in the Normal state and cascades restoration to the co-deleted subtree. |
| `18` | `0x040000` | `PURGE` | Directory / Document | Soft-Deleted | Physically and irreversibly destroy a soft-deleted object and all its revisions; for directories, cascades physical destruction across the soft-deleted subtree. |

#### 2.5 Permission Governance Operations (Directories & Documents)

| Bit Offset | Mask (Hex) | Operation | Applicable State | Semantics & Constraints |
| --- | --- | --- | --- | --- |
| `19` | `0x080000` | `READ_DACL` | Normal | Read an object's DACL rules and `inherit` configuration state. |
| `20` | `0x100000` | `WRITE_DACL` | Normal | Modify an object's DACL rules and `inherit` toggle. |

### 3. Predefined Permission Macros (Presets)

Permission macros are expanded at compile time into atomic operation bitmasks according to the following definitions:

| Macro Name | Expanded Atomic Operations | Typical Use Case |
| --- | --- | --- |
| `CREATE_CHILD` | `CREATE_DOCUMENT`, `CREATE_DIRECTORY` | Create any child object type inside a directory |
| `MOVE` | `REPARENT`, `RENAME` | Full move capability; supports set subtraction such as `[MOVE, -RENAME]` |
| `PRESET_READ` | `TRAVERSE`, `LIST_DIRECTORY`, `READ_CONTENT`, `READ_METADATA` | Standard read-only browsing |
| `PRESET_WRITE` | `CREATE_CHILD`, `MOVE`, `WRITE_CONTENT`, `WRITE_METADATA`, `LIST_REVISIONS`, `SET_CURRENT_REVISION`, `DELETE` | Standard collaborator editing (deliberately excludes `READ_REVISION`, `DELETE_REVISION`, `PURGE`, and ACL governance) |
| `PRESET_RW` | `PRESET_READ`, `PRESET_WRITE` | Full read/write collaboration |
| `PRESET_TRASH_MANAGE` | `LIST_DELETED`, `RESTORE`, `PURGE`, `DIRECTORY_DELETE_CHILD` | Trash maintenance and bulk cleanup |
| `PRESET_ACL_MANAGE` | `READ_DACL`, `WRITE_DACL` | Standard directory and document permission administrator |

### 4. Formal Grammar (Lark / EBNF)

The normative grammar is maintained in a standalone file, `cacl.lark`, satisfying unambiguous LALR(1) constraints:

```lark
// CACL (CFMS Access Control Language) Grammar
// Compatible with Lark LALR(1) parser.

start: directive* rule*

directive: "inherit" inherit_state ";"
inherit_state: "on"  -> inherit_on
             | "off" -> inherit_off

rule: effect op_set scope_clause? match_clause remark_clause? ";"

effect: "allow" -> effect_allow
      | "deny"  -> effect_deny

op_set: "[" op_item ("," op_item)* "]"
?op_item: op_add | op_sub
op_add: IDENT
op_sub: "-" IDENT

?scope_clause: "on" scope
scope: "self" -> scope_self
     | "dirs" -> scope_dirs
     | "docs" -> scope_docs
     | "all"  -> scope_all

?match_clause: "to" principal_list
             | "when" bool_expr

principal_list: principal ("," principal)*
?principal: principal_pred | any_pred

?bool_expr: or_expr
?or_expr: and_expr ("or" and_expr)*
?and_expr: not_expr ("and" not_expr)*
?not_expr: neg_expr | atom
neg_expr: "not" not_expr

?atom: principal_pred
     | perm_pred
     | any_pred
     | "(" bool_expr ")"

principal_pred: PRINCIPAL_KIND "(" STRING ")"
perm_pred: PERM_KIND "(" STRING ")"
any_pred: "any"

remark_clause: "remark" STRING

PRINCIPAL_KIND: "user" | "group" | "role"
PERM_KIND: "perm"
IDENT: /[A-Z][A-Z0-9_]*/
STRING: /"([^"\\\r\n]|\\.)*"/
COMMENT: /#[^\r\n]*/

%ignore /[ \t\r\n]+/
%ignore COMMENT

```

#### Syntactic Equivalence Rules

* `to p1, p2, ...` is **strictly equivalent** in both abstract syntax tree (AST) representation and evaluation semantics to `when p1 or p2 or ...`; it carries no precedence advantage over `when`.
* An omitted `scope_clause` defaults to `on all`.
* An omitted `inherit` directive defaults to `inherit on`.

---

### 5. Compile-Time Semantic Validation and Save-Time Authorization

When compiling `.cacl` text into its intermediate representation, the compiler **must** enforce the following checks:

1. **Directive Uniqueness**: At most one `inherit` directive may appear in a single object's policy text; duplicate declarations must raise a compile error.
2. **Set Algebra Validity**: `op_set` is evaluated strictly left to right via set union (unsigned items) and set difference (`-` prefixed items). The leading item must not be negative; every identifier must be a valid atomic operation or predefined macro; an empty resulting bitmask must raise a compile error; subtracting a bit not currently present in the accumulated set should emit a compiler warning.
3. **Scope Intersection Warnings**: If a rule specifies `on dirs` but its expanded bitmask contains no directory-applicable operations, or specifies `on docs` but contains no document-applicable operations, the compiler should emit a warning.
4. **Commit-Time Permission Enforcement**: When persisting compiled output (including any change to DACL rules or the `inherit` toggle), the server must verify that the acting subject holds `WRITE_DACL` on the target object.

---

### 6. Runtime Evaluation Pipeline

For any authorization request `(subject, target_object, requested_op)`, the evaluation engine renders a deterministic decision in the following order:

1. **Lifecycle State and Endpoint Boundary Validation**:
* Standard business endpoints are guarded by the global soft-delete filter; soft-deleted objects are invisible externally, and only operations applicable to the Normal state are accepted.
* When dedicated trash management endpoints bypass the global filter and encounter a soft-deleted target object, **only** `LIST_DELETED` (directories only), `RESTORE`, and `PURGE` may proceed to subsequent evaluation; all other operations are immediately denied.
* **Internal Bypass Convention**: When evaluating trash operations, the authorization engine itself must bypass the global filter to load rules from the target object and its ancestor chain, while strictly prohibiting any unauthorized disclosure of rule contents.


2. **Path Traversal Check**: Validate `TRAVERSE` permission on all ancestor directories along the target path in accordance with system configuration.
3. **DACL Inheritance Chain Assembly**:
* Collect DACL `allow` and `deny` rules upward starting from the target object, filtering by `scope`.
* Upon encountering a node configured with `inherit off`, **retain that node's own rules and immediately stop traversing upward**.


4. **Deny-Overrides and Default Deny**:
* Within the effective DACL rule set, if any `deny` rule matches `requested_op` and evaluates to true, return **DENY**.
* Otherwise, if any `allow` rule matches `requested_op` and evaluates to true, return **ALLOW**.
* If no rule matches, fall back to the default policy and return **DENY**.


5. **Cross-Object and Cascading Composite Constraints**:
* Executing `REPARENT` (including cross-directory moves initiated via `MOVE`) requires `REPARENT` on the source object and `CREATE_DOCUMENT` (for documents) or `CREATE_DIRECTORY` (for directories) on the destination parent directory.
* Executing `DIRECTORY_DELETE_CHILD`, directory-level `RESTORE`, or directory-level `PURGE` authorizes cascading lifecycle transitions across the target directory's subtree without requiring per-child DACL checks, subject to object state invariants (such as requiring the target parent directory to be in the Normal state before `RESTORE`).

## Usage Examples

### Example A: Revision Restrictions and Fine-Grained Collaborator Grants

```cacl
inherit on;

# Prohibit reading or destroying historical revisions without audit clearance
deny [READ_REVISION, DELETE_REVISION] on docs
  when not perm("history_audit")
  remark "Prevent historical snapshot leakage and audit trail tampering";

# External collaborators may edit content, but cannot rename or soft-delete
allow [PRESET_EDIT, -RENAME, -DELETE]
  to user("alice"), group("external_editors")
  remark "External collaborators restricted to content iteration";

# Core R&D with vault write permission, or security auditors, may manage trash
allow [PRESET_TRASH_ADMIN] on dirs
  when (group("core_dev") and perm("vault_write")) or group("sec_auditors");

```

### Example B: Blind Dropbox Directory

```cacl
inherit off;

# All employees may drop new documents here, but cannot list others' files
# or read any child documents
allow [TRAVERSE, CREATE_DOCUMENT] on self
  to group("all_employees")
  remark "Blind dropbox submission entry point";

# Only the review board may list the directory and read submitted documents
allow [LIST_DIRECTORY] on self
  to group("review_board");

allow [READ_CONTENT, READ_METADATA] on docs
  to group("review_board")
  remark "Read-only inspection by the review board";

```

## Backwards Compatibility

This proposal establishes a new baseline specification for the CFMS access control subsystem and is not directly backwards-compatible with legacy unstructured permission rules. Upgrading existing deployments requires an offline migration script performing the following mappings:

* Map legacy `READ_CONTENT` / `WRITE_CONTENT` grants on directories according to node type to `LIST_DIRECTORY` / `CREATE_DOCUMENT | CREATE_DIRECTORY` or the corresponding document read/write operations.
* Split legacy `MOVE` into the two-bit combination `REPARENT | RENAME`.
* Migrate legacy `READ_DELETED_CONTENT` to the directory operation `LIST_DELETED`.

---

## Security Implications

* **Deterministic Deny-Overrides and Default-Deny Baseline**: Evaluating the effective DACL rule set with explicit `deny` overriding `allow`—and falling back to `DENY` when no rule matches—eliminates rule-ordering ambiguity and prevents accidental exposure on newly created or unconfigured nodes.
* **Privilege Boundaries of `WRITE_DACL` and `REPARENT**`: Because `inherit off` truncates ancestor DACL propagation and `REPARENT` transitions an object into a different inheritance hierarchy, `WRITE_DACL` and `REPARENT` carry elevated privilege impact and should be granted strictly to trusted administrators.
* **Preserving Audit Trail Integrity**: Excluding `READ_REVISION`, `DELETE_REVISION`, and `PURGE` from `PRESET_EDIT`—and strictly forbidding deletion of the `current` or sole remaining revision—protects the integrity of immutable revision histories.
* **Preventing Unauthorized Access to Soft-Deleted Data**: Combined with global query filters, constraining soft-deleted capabilities strictly to `LIST_DELETED`, `RESTORE`, and `PURGE` ensures deleted document bodies cannot be covertly read without triggering an auditable restoration event.

## Reference Implementation

The reference implementation consists of two components, with `cacl.lark` serving as the grammatical single source of truth:

1. **Grammar File (`cacl.lark`)**: Defined in full in Section 4 and loaded with table caching via `Lark.open("cacl.lark", rel_to=__file__, parser="lalr", cache=True)`.
2. **Compiler and Intermediate Representation (`acl_compiler.py`)**: Maps the 21 atomic bitmasks using Python's `IntFlag` and employs a `lark.Transformer` to perform macro expansion, set algebra evaluation, scope intersection warnings, and canonical DACL rule emission (`inherit` state and `dacl_rules`).

## Rejected Ideas

1. **Splitting `explicit` and `policy` Keywords**: An earlier draft proposed `explicit allow ... to` and `policy allow ... when` to distinguish static principal grants from dynamic predicates. This risked misleading policy authors into assuming `explicit allow` overrides `policy deny`, introducing severe precedence ambiguity. Both forms were unified into peer-level `allow` / `deny` rules, retaining `to` solely as syntactic sugar.
2. **Retaining `READ_DELETED_CONTENT**`: Because CFMS isolates soft-deleted objects globally via query filters, un-restored objects should never expose body content. Keeping a separate read-deleted-body permission offered no legitimate workflow while expanding unaudited forensic access risks, so it was removed in favor of directory-level `LIST_DELETED`.
3. **Defining `MOVE` as an Atomic Operation Implying `RENAME**`: Non-orthogonal atomic bits create logical contradictions between `allow [MOVE]` and `deny [RENAME]`. Splitting it into orthogonal `REPARENT` and `RENAME` bits and demoting `MOVE` to a compile-time macro makes set expressions like `[MOVE, -RENAME]` completely self-consistent.
4. **Persisting `#` Line Comments in the Database**: Preserving arbitrary `#` comment positions requires maintaining brittle lexical side-channels that easily misalign when rules are edited or reordered. Modeling structured audit notes as first-class `remark` fields aligns much more cleanly with an SSOT decompilation architecture.
5. **Runtime Macro Expansion**: Persisting macro names such as `PRESET_EDIT` and expanding them at runtime would cause future changes to macro definitions to implicitly alter effective permission boundaries on sensitive legacy directories. Expanding macros at compile time guarantees long-term determinism for historical grants.
